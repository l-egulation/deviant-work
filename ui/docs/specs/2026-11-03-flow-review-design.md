# 사용자 흐름도 재정비 설계

작성: 2026-11-03 · 상태: **승인됨 (2026-11-03)**
팀 레포 기준: `d4786611` (2026-11-03) — 작업을 시작할 때 최신 커밋을 다시 확인한다.

## 1. 의도와 이유

와이어프레임은 FigJam 흐름도를 바탕으로 그려 왔다. 그런데 흐름도가 팀 게임과 어긋나 있고 빠진 화면이 많아서, 와이어프레임을 검증할 기준이 없다. 그래서 **흐름도를 먼저 팀 레포 기준으로 바로잡고 빠진 화면까지 채운 다음, 그 순서대로 와이어프레임을 하나씩 검증한다.** 이 문서는 그 첫 단계인 흐름도 재정비만 다룬다.

## 2. 목표 / 비목표 / 피해야 할 것

**목표**

- 팀 게임에 있는 모든 화면·장소·연출을 흐름도에 빠짐없이 넣는다.
- 상자마다 대응하는 와이어프레임 번호와 상태를 달아, 흐름도가 와이어프레임 검증 체크리스트 역할을 하게 한다.
- 사용자가 화면 이름·목적·다음 행동으로 흐름을 따라갈 수 있게 한다(번호만으로 설명하지 않는다).

**비목표**

- 와이어프레임 수정·추가 (다음 단계)
- 테마·시각 디자인
- 팀 레포에 없는 새 기능 제안. 단, 이미 사용자가 정한 예정 변경은 메모로 단다.

**피해야 할 것**

- 화살표가 겹치거나 반대 방향처럼 보이는 배치 (사용자가 전에 지적함)
- 팀 레포에 없는 규칙을 확정된 것처럼 그리기
- 기존 섹션을 지우기 (이전안으로 내리고 보존)

## 3. 기준

- **사용자가 방향을 정한 부분은 사용자 안을 본 흐름으로 그리고, 지금 팀 구현은 메모로 단다. 그 밖의 부분은 팀 레포 기준으로 그린다**(사용자 결정 2026-11-03).
- 메모 색은 하나로 정해 "팀 현재 구현: …"으로 쓰고, 해당 상자 옆에 붙인다. 지금 사용자 안이 본 흐름인 곳은 두 군데다.
  - **타이틀:** 사용자 와이어프레임(새 게임·이어하기·설정·제작진·종료, 종료 확인, 설정 3항목)이 본 흐름이다. 메모는 "팀 현재 구현: 시작하기·종료".
  - **챕터 진행:** 각 챕터 보스 → 제단 → 출구 → 다음 챕터로 바로 이어진다. 결과 화면은 사망·클리어(마지막 챕터, 현재 빌드는 2챕터) 두 가지다. 메모는 "팀 현재 구현: 마을 팔레트 조각 5개 전에는 1챕터 클리어 결과 → 마을 → 장인 장면, 빠질 예정". 조각으로 열리던 마을 작업대 조건은 팀이 대체 조건을 정하기 전까지 현재 조건을 메모로 둔다.
- 새로 사용자 결정이 생기면 같은 규칙으로 본 흐름을 바꾸고 결정 기록에 남긴다.
- **팀의 목표 규칙과 현재 구현이 다를 때**(예: 색상 잉크 보관함 목표 0~5칸, 현재 제한 없음): 현재 구현을 실선 상자로 그리고, 목표 규칙의 분기는 **점선 상자 + "목표(미구현)" 표시**로 함께 그린다. UI는 결국 목표 규칙을 받아야 하기 때문이다. (Claude 판단)
- **와이어프레임 상태 판정:** 와이어프레임을 그 상자의 내용(현재 구현, 점선이면 목표 규칙)과 비교한다. "팀 현재 구현" 메모에만 맞는 경우는 `수정 (팀 현재 구현엔 맞음)`처럼 적는다. (Claude 판단)
- 팀 레포에서 서로 다른 문서가 충돌하면 구현 설명(`run-structure.md`의 "현재 구현", `development/*.md`)을 우선하고, 충돌 자체를 메모로 단다.

## 4. 검토한 방법

| 방법 | 내용 | 결과 |
|---|---|---|
| **A. 전체 흐름 1장 + 구역별 상세 5장** | 큰 고리만 그린 전체 흐름과 구역별 상세. 상자에 와이어프레임 번호·상태 표시 | **선택** — 장마다 화살표가 적어 겹침이 줄고, 체크리스트로 쓰기 좋다 |
| B. 기존 화살표 흐름도 한 장에 전부 추가 | 상자 40개 이상 | 기각 — 엉키고 고치기 어렵다 |

| ⑤ 색상 잉크 획득 | 기존 섹션 내용을 팀 레포 기준으로 재확인(목표 보관함 0~5칸 vs 현재 제한 없음) |

**상자 표기:**

```

```

- 상태 값: `맞음` / `수정` / `없음` / `이전안만 있음`
