# Deviant UI 작업 인수인계

> 2026-11-03 레포 개편으로 `ui/claude-handoff.md`에서 이 위치로 옮겼다. 지금 상태와 다음 할 일은 [STATUS](STATUS.md), 정한 것은 [결정 기록](decisions.md)이 기준이다. 아래 "최신 기준"은 2026-11-03 오전 기준이며, 그 뒤 팀 레포에서 마을 팔레트 조각 규칙이 추가됐다(결정 기록 참고).

## 역할과 현재 목표

Claude는 기존 FigJam 사용자 흐름과 Figma 와이어프레임을 정리하고 기능·정보 구조를 검토한다. GPT와 사용자는 별도로 이미지 생성 등을 이용해 UI 테마를 탐색한다. 게임명은 Deviant다. 사용자는 Unity 게임 UI를 팀과 검토하며, office hour 방식으로 미정 사항을 하나씩 논의하는 것을 선호한다.

지금 가장 필요한 일은 **흩어진 기존 와이어프레임의 상태와 위치를 파악하기 쉽게 정리하는 것**이다. 최신 기준을 확인해 현행·검토 중·이전안을 구분하고, 사용자가 타이틀→마을→탐험→정비→런 결과 순서로 찾을 수 있도록 안내한다. 기존 화면을 보존하면서 정리하고, 설계가 미정인 부분은 확정된 사실처럼 표현하지 않는다.

## 작업물 위치

- [사용자 흐름 FigJam](https://www.figma.com/board/nHfGBYZsYIcHNUD9SU4cGs): 전체 흐름과 상세 흐름. [현행 화살표 흐름](https://www.figma.com/board/nHfGBYZsYIcHNUD9SU4cGs/?node-id=62-377), [색상 잉크 상세](https://www.figma.com/board/nHfGBYZsYIcHNUD9SU4cGs/?node-id=65-452). 사용자는 화살표로 이어진 흐름도를 선호하며 선 겹침과 반대 방향처럼 보이는 화살표를 지적했다.
- [기존 UI 와이어프레임 Figma](https://www.figma.com/design/qjL5PNYHPgTDQ0huZXBzLg): Page 1에 01~51 화면이 배열되어 있다. 현재안·수정 대상·이전안이 혼재한다. 01~15는 타이틀·설정 관련 오래된 검토안, 16~47은 정비·인벤토리·장비·색상 잉크 화면이며 많은 것이 이전안 또는 수정 대상으로 표시돼 있다. 48~51은 [사망·런 완료 결과 4상태](https://www.figma.com/design/qjL5PNYHPgTDQ0huZXBzLg/?node-id=74-75)다. 각 상태는 편집 가능한 레이어로 만들어졌다. 번호 자체는 현재성의 증거가 아니다.
- [UI 작업 브랜치](https://github.com/l-egulation/deviant-work/tree/work/ui-design/ui): UI 자료와 인수인계 기록. [결과 화면 정보 구조](../work/specs-screens/result-screens.md), [UI 안내](../README.md). HTML 결과 화면은 이전 참고안이며 Figma가 현재 검토 대상이다. 이 브랜치의 오래된 문서와 README 일부는 현행 규칙과 다를 수 있다.
- 게임 원본: [SSAFY 게임 저장소](https://lab.ssafy.com/s15-final/S15P31F109.git). 접근 가능하면 저장소의 최신 브랜치·커밋 시점과 문서 및 구현 상태를 확인한다. 접근이 불가능하면 사용자에게 현재 자료를 요청하고 확인하지 못한 부분을 명시한다.

## 최신 기준과 문서 충돌

**2026-11-03에 확보한 저장소 사본을 검토한 기준**이며 이후 변경될 수 있다. 게임 저장소의 `docs/design/run-structure.md`, `docs/development/chapter2-runtime.md`, `docs/design/chapter2-layout.md`, `docs/getting-started/playtest.md` 기준은 다음과 같다.

1. 현재 공통 빌드는 타이틀→시작 마을→출발 준비대에서 서로 다른 도면 2개 선택→1챕터 탐험. 제품 전체의 최초·반복 런 지급 규칙까지 확정됐다는 의미는 아니다.
2. 무기별 출발 팔레트는 기본 3칸이며 영구 해금으로 4·5칸이 열린다. 과거 대화의 별도 팔레트 획득 및 기본 5칸 가정은 구안이다.
3. 1챕터 보스 후 색상 잉크 제단과 출구를 거쳐 **결과 화면 없이 같은 런으로 2챕터 진입**. 장비·팔레트·체력·가방·골드를 유지한다. **(2026-11-03 오후 팀 변경: 마을 팔레트 조각 5개를 모은 뒤의 런에만 해당한다. 그 전에는 1챕터 클리어 결과 → 마을. [결정 기록](decisions.md) 참고)**
4. 사망 또는 현 빌드의 마지막 챕터인 2챕터 완료 시 결과 화면→마을로 이동한다. 목표 게임은 3챕터이므로 최종 완료 시점은 차후 갱신해야 한다.
5. 사망은 죽는 모션 뒤 실제 시간 2.5초 후 결과 화면을 연다. 결과에 시간·처치 수·이번 런의 마법안료가 표시된다. 마법안료는 적 처치 시 이미 지급되는 영구 재화다.
6. 색상 잉크 제단, 보관함 용량, 정비 및 획득 규칙의 상세는 `docs/design/systems/ink-blueprint-proposal.md`, `roguelite-progression.md`, `progression-and-economy.md`와 실제 구현을 함께 확인한다. 목표 규칙과 구현 차이를 표시한다.

`docs/design/player-flow.md` 및 `ui-and-interaction.md` 등에는 이전 1챕터 결과·마을 귀환 문구가 남아 있는 것으로 확인됐다. 문서의 작성 시점과 구현을 대조하고 차이를 기록한다. 이전 office hour 결정도 팀 최신 개편안과 충돌하면 그대로 확정 취급하지 않는다.

## 지금까지의 진행과 검토 시 주의

- 초기에는 기본 무기 2개 무작위 지급, 첫 정비소에서 팔레트 획득, 팔레트 기본 5칸, 룰렛 직후 적용 등을 office hour로 논의했다. 이후 팀의 개편안과 게임 저장소 기준이 바뀌었으므로 과거 합의를 현행 규칙으로 그대로 가져오지 않는다.
- 화면 정리는 여러 차례 진행했으나 같은 페이지에 이전안과 수정 대상이 여전히 혼재한다. 48~51 결과 화면은 정보 구조를 검토하기 위한 초안이며 제목·숫자·배치는 확정 디자인이 아니다.
- 사용자는 화면 번호나 강의 워크북 번호만으로 설명하면 이해하기 어렵다고 했다. 화면 이름, 목적, 진입과 다음 행동을 함께 적는다.
- 피그마에서 직접 검토하고 편집하는 방식을 선호한다. 결과 화면을 HTML로 따로 만들었을 때 사용자에게 접근과 맥락이 불편했고, 이후 기존 Figma 파일에 다시 만들었다. HTML은 보조 참고다.
- 마지막 흐름도 수정에서 1챕터 출구 뒤를 2챕터 진입으로 바꿨다. 그 이전의 마을 귀환 표기는 오류였다. 흐름도는 전체 게임의 모든 예외를 완성했다는 뜻이 아니므로 현재 저장소와 다시 대조한다.
- 1챕터의 제단은 보스 처치 후 등장하고 사용 여부는 선택이다. 후보를 고르지 않은 채 출구로 떠날 때의 동작 등은 게임 저장소 구현과 설계의 차이를 확인한다. 현행 Unity 보관 용량과 목표 보관함 규칙 역시 차이가 있다.
- 게임 기획 자료가 바뀔 수 있으므로 저장소의 커밋과 확인 날짜를 기록하고, 설계 목표·실제 구현·이전 사용자 논의·새 제안을 구분한다.

## 작업 방식과 주의

- 사용자는 처음부터 새 UI를 설계한다고 생각한다. 기존 임시 게임 화면은 참고이며 확정된 아트 방향은 아니다.
- 전투 도중 정비 기능을 쓰는 구조로 임의 설계하지 않는다. 인벤토리·장비창은 언제든 열 수 있고 열면 일시정지하기로 논의했으나 최신 구현과 재확인한다.
- 흐름도와 화면은 서로 참조할 수 있어야 한다. 확정·구현·제안·미정의 근거를 구분한다.
- Figma 정리 시 먼저 전체 프레임과 연결을 살펴보고 화면별 상태를 판정한다. 불확실한 상태는 검토 중으로 둔다. 한눈에 찾는 인덱스와 섹션을 만들고, 이동 후 화면이 겹치거나 링크가 끊기지 않았는지 확인한다.
- 새 화면을 계속 늘리기 전에 필요한 화면 목록, 현재 위치, 빠진 화면, 의사결정을 정리한다.
- 사용자에게 질문할 때 게임 용어를 설명하고 실제 선택 상황을 예로 든다. 복잡한 질문을 한꺼번에 확정하도록 요구하지 않는다.
- 작업 결과·판정 근거·남은 질문을 `deviant-work` 저장소의 `work/ui-design` 브랜치에 기록한다. 게임 원본 저장소는 근거 확인 대상으로 취급하고, 수정이 필요한 경우 해당 저장소의 작업 규칙과 사용자 지시를 확인한다. 피그마 링크를 함께 남겨 원격에서도 찾을 수 있게 한다.

## 테마 작업과의 경계

테마는 GPT와 사용자 쪽에서 이미지 생성 및 방향 비교를 진행한다. 잉크·스케치 콘셉트이고 지나치게 동양풍일 필요는 없다. 기존 임시 게임 캡처는 보라색 픽셀 숲과 어두운 테두리 UI를 보여주지만 최종 스타일로 확정된 것은 아니다. Claude는 와이어프레임의 기능과 정보 구조를 우선 정리하고, 테마 결정이 필요한 부분을 표시한다. 최종 선택한 테마를 이후 대표 화면과 컴포넌트에 반영할 수 있도록 화면 구조를 편집 가능하게 유지한다.

## 권장 첫 결과

1. 현행 게임 문서와 Figma를 확인한 화면 목록 및 상태 판정.
2. Figma에 현행·검토 중·이전안을 찾을 수 있는 정리 구조와 간단한 안내.
3. 사용자 흐름과 화면 사이의 빠진 연결 및 최신 규칙 충돌 목록.
4. 팀 확인이 필요한 질문과 다음 작업 순서. 실질적 판단이 어려운 항목은 미정으로 남긴다.
